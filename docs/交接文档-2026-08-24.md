### 2.3 数据库操作方式

宿主机无 mysql 客户端，必须通过容器执行：

```bash
# 查询（注意 --default-character-set=utf8mb4，否则中文会乱码）
docker exec changping-mysql mysql -uroot -p'<见 docker/.env>' --default-character-set=utf8mb4 zhsq -e "SELECT ..."

# 执行 SQL 文件（推荐用于含中文的 INSERT，避免 docker exec 传参编码问题）
docker exec -i changping-mysql mysql -uroot -p'<见 docker/.env>' --default-character-set=utf8mb4 zhsq < /path/to/file.sql
```

数据库密码见 `/opt/zhsq/repo/docker/.env`（`MYSQL_ROOT_PASSWORD=<见 docker/.env>`）。

### 3.2 政策资源库（逻辑梳理 + 测试数据）

**功能链路**：管理端政策 CRUD → 「政策找人」匹配人口 → 「定向推送」按手机号关联居民账号写站内通知 → 居民端 H5「政策查询/消息」查看。

**核心代码**：
- 控制器：`backend/.../community/controller/PolicyResourceController.java`
- 服务：`backend/.../community/service/PolicyResourceService.java`
- 表：`cmn_policy_resource`（V70 建表，V84 内置 5 条样本政策）
- 管理端页面：`web/src/views/PolicyResourceView.vue`；居民端：`h5/pages/resident/policies/index.vue`

**政策找人匹配算法**（findMatchingPeople）：
```
cmn_population WHERE status='ACTIVE'
  AND household_type IN (政策类型→户籍类型映射)
  [AND tags LIKE 政策 tags 任一标签（%tag% 模糊）]   -- 政策有 tags 时才过滤
LIMIT 500
```
类型映射（resolveHouseholdTypes）：
- LOW_INCOME(低保) → [LOW_INCOME]
- ELDERLY(养老) → [SPECIAL_CARE, LOCAL, NON_LOCAL]
- RESCUE(救助) → [LOW_INCOME, SPECIAL_CARE, FLOATING]
- MEDICAL(医保) → [LOCAL, NON_LOCAL, FLOATING]
- BENEFIT(惠民) → [LOCAL, NON_LOCAL, FLOATING, LOW_INCOME, SPECIAL_CARE]
- 其他 → [LOCAL, NON_LOCAL]

**定向推送**（pushToResidents）：匹配人群按手机号去重 → 关联 `sys_user`（role_code='PUBLIC' 且 deleted=0 status=ACTIVE）→ 逐人写 `sys_notification`（type=POLICY, related_type=POLICY, related_id=政策ID，标题=政策标题，内容=政策说明前200字）→ 返回 `{matched, pushed, noAccount, message}`。写入走 NotificationBatchWriter 批量队列。

## 4. 经验教训 / 坑（务必传给下一位）

### 4.1 docker exec 传中文 → 数据库乱码（本次最大坑）
- **现象**：`docker exec changping-mysql mysql ... -e "INSERT ... 中文"` 时，中文被双重编码（mojibake）入库（HEX 为 `C3A4C2BD...` 而非 `E4BD8E...`）。查询时若连接字符集与存储不一致则 LIKE/匹配失败，但某些连接下显示正常（双向乱码假象），极具迷惑性。
- **规避**：含中文的 SQL 一律写成文件，用 `docker exec -i ... mysql --default-character-set=utf8mb4 < file.sql` 执行。
- **排查技巧**：用 `HEX(列)` 验证存储编码；用 MySQL general_log（`SET GLOBAL general_log=ON; log_output=TABLE`）抓真实 SQL。

### 4.2 政策找人"匹配不到人"的常见原因
1. 人口 `tags` 为空/无对应标签 → 标签 LIKE 过滤掉（养老政策对无标签人口返回 0 属正常）
2. 人口 `status != 'ACTIVE'`（如 NULL）→ 不匹配（原 id 17-20 即为 NULL，被过滤）
3. 数据乱码（见 4.1）
4. 户籍类型与政策映射不符（如 LOW_INCOME 政策只匹配 LOW_INCOME 人口）

### 4.3 部署版本不一致风险
- 线上容器构建时间可能早于代码提交（如 backend jar 为 2026-08-21 构建）。**排查问题时先对比容器内产物与源码**（可 `docker exec` 进容器反编译 class / grep dist JS 验证）。
- 改完代码记得 `git push` + 重新构建对应容器，二者缺一不可。

### 4.4 用户推送的代码，服务器构建可能失败
- 用户本地可能未跑 `vue-tsc` 类型检查（或环境宽松），代码推上来后服务器 `npm run build` 报 TS 错误。修复思路：以 `api/index.ts` 的导出类型为准改本地重复定义。

### 4.5 冒烟测试接口路径易错清单（都是踩过的）
- 事件列表 = `/api/events`（不是 /event/events），返回结构 `data.items`
- 人口 = `/community/population`（单数）；审计日志 = `/audit-logs`；台账 = `/ledger/data/{TYPE}`（TYPE 必须大写枚举，小写走 default 返回空列表）
- `/integrations/alarms` 只有 `POST /callback`（第三方报警回调接收），**没有列表接口**，测试时别误判为 bug
- 登录 = `/api/auth/login`；字典项 = `/system/dicts/{code}/items?activeOnly=true`

### 4.6 视频点位接入的架构与网络现实
- **网络现实**：服务器在阿里云公网，办公室内网摄像头不可达。可行方案：办公电脑中转转流、frp 内网穿透、GB28181 注册到公网（摄像头主动出站）、路由器端口映射。
- **流类型与播放方式**（后端 `VideoCameraService`）：
  - `streamType=RTSP` → 后端自动把播放地址转为 `/api/video/stream/{id}/index.m3u8`，从宿主机 `/opt/zhsq/video-hls/{deviceNo}/` 读（容器内挂载 `/app/video-hls`）
  - HLS/FLV → `streamUrl` 直连浏览器播放（前端已内置 hls.js + flv.js）
  - `proxy://设备编号` → 演示点位，走 HLS 转流目录
- 转流目录当前只剩 `record-cron.log`（CAM-008-* 目录已随回滚删除）
