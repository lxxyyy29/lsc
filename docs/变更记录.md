## 2026-10-18 违停回调补充协议：新增「所属网格」gridName（V135）

**对端诉求**（`接口协议补充稿.docx`）：板端在既有 `POST /api/integrations/alarms/callback` 中新增可选字段
`gridName`（string，人工填写、去首尾空白、最多 60 字），平台按文本接收/保存，并展示到事件基本信息的
「所属网格」。**不新增接口、不涉及网格实体匹配或 grid_id 绑定**，鉴权/重试/响应规则不变。

### 实现

| 层 | 改动 |
|---|---|
| 数据库 | **V135**：`biz_event` 新增 `grid_name VARCHAR(60) NULL`（`AFTER grid_id`），注释标明为回调文本 |
| 归一化 | `AlarmEventMongoService.normalize()` 读取 `gridName`（兼容 `grid_name`），trim + 截断 60 字，空串视为未提供；写入 `normalizedPayload.gridName` 便于追溯 |
| 存储 | `NormalizedAlarmEvent` 增 `gridName`；`EventProjectionBridgeService` 写入 `biz_event.grid_name`（**不写 grid_id**）；Mongo `alarm_events` 同步存 `gridName` |
| 展示 | `EventServiceImpl` 的详情/列表投影：`firstNonBlank(entity.gridName, document.gridName, resolveGridName(gridId))` → 优先用回调文本，未提供时回退原网格实体解析；页面 `EventDetailView.vue` 原本就有「所属网格」行，无需改动 |

### 实测（生产，4 条用例，测完已通过 `/events/batch-delete` 清理，DB 与 Mongo 均无残留）

| 用例 | 输入 | 结果 |
|---|---|---|
| 1 | `"第3网格"` | 入库 `第3网格`，详情接口 `gridName=第3网格`，Mongo 同步 |
| 2 | `"  第4网格  "` | 首尾空白已去除 → `第4网格` |
| 3 | 80 个汉字 | 截断为 60 字（`CHAR_LENGTH=60`） |
| 4 | 不传 `gridName` | 入库 `NULL`，Mongo 无该字段，页面显示 `-`（兼容旧配置） |

- 生产当前 `pendingRelease=226`（10-16 夜 118 条 + 10-17 夜 108 条）：按 B 方案不再自动恢复，

## 2026-10-17 夜间抑制语义修正（B 方案）：白天也保持隐藏，改为人工放出

**起因**：10-16 夜间抑制首次真实生效，17:30–09:00 共抑制 **118 条**无人机违停抓拍；
09:00 到点按 v1 设计全部自动恢复显示，白天一次性涌入事件列表（全部待派单、无工单），
业务反馈「我不是进行抑制了吗，昨天晚间的事件还能看到」——等于没静默。

**决策**（业务方选定 B 方案）：夜间抑制的事件**白天也保持隐藏**，窗口结束不自动恢复，必须人工放出。

### 一、行为变更

| 场景 | 变更前（v1） | 变更后（B） |
|---|---|---|
| 抑制窗口内 | `hidden=1`、不派单、不通知 | 不变 |
| 窗口结束 | 自动 `hidden=0`，白天回到列表待派单 | **保持 `hidden=1`**，只统计为「待放行」 |
| `suppress_released_at` | 到点自动恢复时间 | **人工放出时间**（窗口结束不写） |
| 放出方式 | 仅单条「强制放出」 | 单条「放出」+ 顶部一键「放出待放行 N 条」 |
| 放出后 | — | `hidden=0`、`suppress_manual=1`；窗口已过，`NO_DISPATCH/NO_NOTIFY` 自然不再拦截 |

### 二、代码

- `SuppressReleaseTask`：**不再写库**（原来是 `hidden=0` + 同步 Mongo）。改为每分钟统计
  「窗口已结束、仍隐藏、未放出」的条数，条数变化时打一条日志；避免夜间数据被静默放回白天列表。
- `EventServiceImpl.setSuppressManual`：`manual=true → hidden=0/manual=1/released_at=NOW()`；
  `manual=false → hidden=1/manual=0/released_at=NULL`（不再有「窗口内/窗口外」分支）。
- 新增 `EventServiceImpl.releasePendingSuppress(limit)` + `PUT /api/events/suppress-manual/release-pending`：
  批量放出待放行事件（默认 200、上限 500），逐条同步 Mongo，返回放出条数。
- `SuppressWindowService.summary()`：新增 `pendingRelease`（待放行，主指标）；
  `releasedRecently` 改为「近 12 小时**人工**放出」，避免与自动恢复混淆。
- Web `EventsView.vue`：提示条改为「N 条仍在抑制时段内 / M 条已到点仍隐藏待放行」+ 一键放出按钮；
  行内标记改为「夜间抑制 / 夜间抑制·待放行 / 夜间抑制·已放出」；弹窗按钮改为「放出 / 收回」。
- Web `SuppressWindowView.vue`：概况条增加「已到点待放行」。
- `docs/夜间时段事件抑制方案.md` 升 v2，文首加「政策变更」以覆盖原文的自动恢复表述。

### 三、生产数据修正（202.168.190.132）

- 10-16 夜间 118 条：`hidden` 由 0 改回 1、清空 `suppress_released_at`（该值是自动恢复留下的，语义已变），
  Mongo `alarm_events` 用 `updateMany` 同步 `hidden=true`（matched=118 modified=118）。
- 修正前 id 清单备份：`/uav_data/backup/suppress_manual_fix_1017152015.tsv`。
- 验证：概况 `pendingRelease=118`；默认列表 total=433（不含夜间抑制），「只看夜间抑制」total=118；
  单条放出/收回 `hidden` 0↔1 正确；批量放出 `limit=2` 返回 2 且随后收回后仍为 118；
  今日 09:00 后新入库 72 条、0 条被抑制（窗口外正常）。

### 四、遗留

1. 待放行的 118 条目前保持隐藏，需业务在「事件闭环处置 → 只看夜间抑制」里批量放出后逐条处置或删除。
2. `SuppressReleaseTask` 类名已与实际职责（只统计不放行）不符，后续可改名 `SuppressPendingTask`。

## 2026-10-16 时段抑制（夜间静默）收尾：不派单 / 不通知 / 强制放出 / 总开关 + 上线实测

承接 8a6e0b9（规则管理 + 入库判定）与 960e32b（复用 hidden 生效 + 到点自动恢复），本次补齐剩余动作与运维手段，
并在生产（202.168.190.132）完成端到端实测（18 项断言全通过）。

### 一、数据库（Flyway V134）

| 变更 | 说明 |
|---|---|
| `biz_event` 新增 `suppress_actions` | 记录本次生效的抑制动作（`HIDE,NO_DISPATCH,NO_NOTIFY`），供派单/通知入口按动作精确判定 |
| `biz_event` 新增 `suppress_released_at` | 抑制解除时间（到点自动恢复或人工放出时写入），+ `idx_biz_event_suppress_released_at` |
| 存量补写 | 已有 `suppress_until` 的行按「全部动作」保守补写 `suppress_actions`；已过期的补记 `suppress_released_at` |

**为什么加 `suppress_actions`**：`biz_event` **没有 `dispatchable` 列**（详情里的 `dispatchable` 来自工作流快照/Mongo），
原计划的 `UPDATE biz_event SET dispatchable = 0` 是无效写入（异常被 try/catch 吞掉，静默失效）。
且三个动作在后台可独立勾选，只勾「不显示」时夜间事件仍应正常派单与通知，因此必须按动作而非仅按时间判定。

**为什么加 `suppress_released_at`**：原自动恢复任务会清空 `suppress_until/rule_id`，导致「昨夜抑制过哪些事件」
无迹可查，无法支撑列表标记与白天提示。改为**只恢复显示、保留抑制痕迹**（`suppress_released_at` 作幂等标记）。

### 二、后端

| 位置 | 改动 |
|---|---|
| `ThirdPartyAlarmIngestService` | 命中时一次写入 `suppress_until / suppress_rule_id / suppress_actions`；删除对不存在的 `dispatchable` 列的写入 |
| `SmartDispatchService.smartDispatch` | 仅当 `suppress_actions` 含 `NO_DISPATCH` 且窗口未结束时抛 `EVENT_IN_SUPPRESS_WINDOW`（不读 `dispatchable`） |
| `NotificationService.createNotification`（唯一通知入口） | 注入 `JdbcTemplate`；`relatedType=EVENT` 且该事件处于抑制中且含 `NO_NOTIFY` → 直接返回不发通知；判定异常时放行（通知优先） |
| `SuppressReleaseTask` | 扫描条件加 `suppress_released_at IS NULL`；恢复时只置 `hidden=0` 并记 `released_at`，不再清空抑制痕迹 |
| `SuppressWindowService` / `Controller` | 新增 `GET/PUT /api/system/suppress-windows/global`（总开关 + 时区，写 `sys_config.suppress.enabled/timezone`）、`GET /summary`（当前抑制中 + 近 12 小时自动恢复条数） |
| `EventController` / `EventService(Impl)` | 新增 `PUT /api/events/{id}/suppress-manual`（强制放出/收回，同步 Mongo；`manual=false` 时若窗口未结束则重新隐藏）；`/events/sections/*` 新增 `suppressOnly` 筛选并返回 `suppressUntil/suppressActions/suppressManual/suppressReleasedAt` |

## 2026-09-11

### 实有人口「户」建模与户主变更关系联动（未提交）

> 背景：反馈两个问题——① 无法把新增人员挂到具体户口下；② 户主变更后其他成员「与户主关系」不跟着变。
> 根因：`cmn_population` 原先没有"户"实体，只有 `address` 字符串 + `relation` 字符串；"户"是查询时按地址临时分组的展示手法，没有户主外键、没有成员归属，因此既无法挂户，也无法在户主变更时推算关系。

#### 一、数据库（Flyway V124）

| 变更 | 说明 |
|---|---|
| 新增 `cmn_household` | 户表：户号 / 地址 / 网格 / `head_population_id`（户主）/ 户籍类型 / 状态 |
| `cmn_population` 新增 `household_id` | 归属户，附 `idx_pop_household_id` 索引 |
| 存量归户 | 按 `网格 + TRIM(地址)` 建户并回填 `household_id`（仅常驻、有地址；流动人口不建户）|
| 指定户主 | 每户取 `relation='户主'` 的成员（多个取最小 id）；无标记的户留待管理端设置 |

#### 二、后端

- 新增 `HouseholdEntity` / `HouseholdVo` / `MemberChangeVo`
- 新增 `HouseholdMapper`、`HouseholdService` / `HouseholdServiceImpl`、`HouseholdController`（`/community/household`，复用 `menu:community:population` 权限）

- `/api/resident/**` 仅限 WEB 客户端属**预期设计**：前端账号密码登录为两段式（先试 H5 失败静默 → 再试 WEB），居民走 WEB 登录后 clientType=WEB，互动接口正常
