# 双端 Figma 1:1 复刻设计（第一批冻结范围）

## 1. 目标

本轮工作的唯一目标是：

- 以用户提供的 Figma 文件为唯一视觉基线
- 对 Web 管理端与 H5 移动端第一批冻结页面进行**严格视觉 1:1 还原**
- 由主 agent 统一调度，多 agent 并行推进
- 在视觉高保真复刻的同时，保持现有业务语义、接口契约、路由语义、权限边界与主链路闭环连续

本轮不再接受“语义接近”“模板化映射”“风格一致但结构不同”作为完成标准。

## 4. 核心原则

## 4.1 视觉高保真优先

本轮首先追求的是**视觉结构与交互外观对齐 Figma**，包括：

- 壳层结构
- 页面主分区
- 区块顺序
- 间距节奏
- 圆角、边框、阴影、背景层级
- 标题区、筛选区、内容区、操作区的位置关系
- 按钮主次层级
- 状态块、标签、统计卡、详情段落的视觉组织

不再以“语义差不多”视为通过。

## 4.2 业务连续性不可回退

视觉再像，只要破坏以下任一项，都不算通过：

- 登录提交流程
- redirect / fallback redirect
- 菜单权限连续性
- 按钮权限连续性
- 列表筛选与详情跳转
- 同组件路由切换
- 提交流程与提交中状态
- Web / H5 退出登录路径
- 只读 / 无权限态表达

## 4.3 主线冻结共享基线，子线并行做页面

为了避免再次滑向“模板化但不一致”的结果，主线必须先冻结：

- Web 壳层基线
- H5 壳层基线
- 页面容器与主分区规则
- 主次按钮与状态块样式基线
- 退出登录、导航激活、空态/错误态/加载态的统一表达

这里的“先冻结”仅指先定义统一基线，并不意味着壳层先单独交付、业务页后补。实际落地必须按用户确认的口径，在同一批次内由壳层包与业务页包并行推进，并以“壳层 + 业务页整组完成”作为验收单位。

## 4.4 不为凑界面新增伪能力

如果 Figma 里存在当前项目没有真实支撑的字段、动作、统计块或入口：

- 不允许伪造业务数据冒充已完成
- 不允许随意新增接口或篡改协议
- 不允许用误导性占位假装可用
- 只能登记为差距项 / 延期项

## 5. 实施架构

采用 **“页面分片并行 + 主线统一壳层与验收基线”** 的方案。

### 5.1 主 agent 职责

主线负责高耦合与高风险事项：

1. 统一 Web / H5 壳层基线
2. 统一共享视觉基线
3. 统一共享行为基线
4. 统一 Figma 对照方法与验收清单
5. 合并后进行 focused / integration 验证
6. 更新 tracking matrix，禁止把模板化重构误记为 1:1 完成

### 5.2 第一批闭环主链路定义

为避免第一批范围解释漂移，本轮闭环主链路明确冻结为：

### Web 主链路

`/login` → `/dashboard` → `/events` → `/events/:id` → `/audits` → `/audits/:id` → `/work-orders` → `/work-orders/:id`

### H5 主链路

主通路明确冻结为：

`/login` → `/workbench` → `/work-orders` → `/work-orders/:orderNo` → `/verify`

第一批内的附属闭环页面与返回语义明确冻结为：

- `/history`：必须可从底部导航直接进入，并保持返回后仍回到当前 H5 主壳层语义中
- `/mine`：必须可从底部导航直接进入，并在页内完成退出登录
- `/verify` 提交或返回后，不得破坏回到主壳层可达页面的既有流转语义
- `/history` 与 `/mine` 不作为主通路中的强制串行前置节点，但属于第一批必须完成并验收的闭环配套页面

以上链路用于约束：

- 第一批 integration test 覆盖范围
- redirect / fallback redirect / 返回流转语义
- 页面间导航连续性
- “第一批完成”声明的最小业务闭环

### 5.3 并行工作包

建议拆成 6 个并行包：

#### 包 A：Web 登录 + Web 壳层

- `/login`
- Web 顶部栏、侧边导航、账号区、退出登录、通用页头

#### 包 B：Web 驾驶舱 + 事件中心

- `/dashboard`
- `/events`
- `/events/:id`

#### 包 C：Web 审核中心 + 工单中心

- `/audits`
- `/audits/:id`
- `/work-orders`
- `/work-orders/:id`

#### 包 D：H5 登录 + H5 壳层

- `/login`
- 移动端顶部区、底部导航、壳层退出、通用移动容器

#### 包 E：H5 工作台 + 工单

- `/workbench`
- `/work-orders`
- `/work-orders/:orderNo`

#### 包 F：H5 核查 + 历史 + 我的

- `/verify`
- `/history`
- `/mine`

### 5.4 拆包原则

- 同一业务链路尽量放在同一包
- 共享壳层不让多个 agent 同时主改
- 每个包绑定自己的一组测试文件
- 页面视觉复刻与行为保持同时完成，不允许只画 UI 不收口行为

## 8. 测试与验证策略

## 8.1 focused tests

focused tests 需要证明：

- 页面关键区块存在
- 页面关键文案与按钮存在
- 状态态被单独覆盖
- 页面不是只保留旧结构换文案

## 8.2 integration / shell tests

integration tests 需要证明：

- 壳层结构可用
- 导航可达
- 登录后跳转连续
- redirect / fallback redirect 连续
- 退出登录正确工作
- 权限回退与首个可访问页面回退不坏

## 8.3 tracking matrix 规则

tracking matrix 只能记录**按新口径真正达到 1:1 的页面**。

如果某页当前只是：

- 统一模板映射
- 风格接近
- 语义保留但结构不一致

则必须回退为：

- 未完成
- 待复核
- 或进行中

不能继续标注为“已完成复刻”。

---

每个页面在 focused / integration tests 之外，还必须附带逐区块 visual 验收包。每个 route 至少包含：

1. 对应 Figma node / variant 标识
2. 默认态对照清单
3. 所有必需状态态对照清单
4. 差距项清单（如有）
5. 当前页面是否允许标记为“1:1 完成”的结论

逐区块 checklist 最少覆盖：

- 壳层
- 标题区 / hero
- 筛选区 / 工具栏（如适用）
- 内容区 / 列表区 / 详情区
- 操作区
- 对应状态页

未完成上述 visual 验收包，不得标记为 1:1 完成。

## 9. 验收标准

## 9.1 视觉验收

每个页面必须满足：

1. 壳层一致
2. 页面结构一致
3. 关键样式一致
4. 状态页一致
5. 不再以“语义接近”代替“视觉对齐”

## 9.2 行为验收

每个页面必须满足：

- 登录流程保持
- redirect / fallback 保持
- 菜单权限保持
- 按钮权限保持
- 列表筛选、详情跳转、同组件路由切换保持
- Web / H5 退出登录可用且路径正确
- 只读 / 无权限态不丢

## 9.3 第一批完成定义

只有当以下条件全部满足，才允许声明第一批完成：

- 第一批冻结页面全部完成
- 所有规定状态态全部完成
- Web / H5 退出登录都已完成并验证
- focused / integration tests 通过
- tracking matrix 与真实实现一致
- 主线复核确认页面已经脱离模板化映射，达到 Figma 高保真收口

---

## 10. 风险与控制

### 9.1 主要风险

- 多 agent 并行时容易产生各页各做各的视觉漂移
- 共享壳层被多人同时修改时容易冲突
- 旧测试可能只证明“页面能打开”，不足以证明“1:1 还原”
- 已有 tracking matrix 状态可能与真实 1:1 完成度不一致

### 9.2 控制策略

- 主线先冻结共享基线再并行
- 共享壳层由主线控改
- 壳层包与业务页包在同一批次内并行推进，并以“壳层 + 业务页整组完成”作为验收单位
- 页面级 focused test 与壳层 integration test 同步更新
- tracking matrix 逐页重验，不沿用旧“已完成”结论

---

## 11. 设计结论

本轮不是对现有页面做样式美化，而是一次**以 Figma 为唯一视觉基线的双端第一批高保真复刻**。

推荐执行方式已经冻结为：

- **严格视觉 1:1**
- **双端并行**
- **壳层与业务页整组推进**
- **闭环主链路作为第一批**
- **所有关键状态态一并收口**
- **主 agent 控共享基线，多 agent 按页面域并行落地**

这份 spec 将直接作为后续 implementation plan 的输入。
