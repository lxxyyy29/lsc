# 东莞常平城管低空巡检事件监管与工单处置平台设计

## 1. 项目目标

基于现有 Figma 初版与《东莞常平城管项目功能描述(1).numbers》需求，规划一套完整的平台方案，最终交付以下三个项目：

1. 后端 Java Spring Boot 项目（JDK 17）
2. Web 管理端项目
3. H5 移动端项目

一期目标是先跑通核心闭环：

**事件进入系统 → 审核流程 → 转工单 → H5 现场处置/核查 → Web 办结确认**

---

## 2. 产品定位

系统定位为：

**低空巡检事件监管与工单处置平台**

它不是单纯的无人机管理系统，也不是单纯的工单系统，而是把以下链路统一起来：

- 无人机平台 / AI 识别提供事件来源
- Web 审核中心负责事件研判与流程审核
- 指挥调度负责派单、转工单
- H5 负责现场核查与工单处置闭环
- 后端统一承载权限、流程、状态机、审计和外部接口适配

---

## 3. 业务范围与关键共识

### 3.1 三端建设范围

- 后端：Spring Boot + JDK17
- Web：管理端，负责审核、流程、派单、配置、看板
- H5：现场端，负责工单处置与现场核查

### 3.2 双主线业务

系统按双主线并行设计，但最终汇聚到统一审核与工单闭环。

#### 主线 A：事件直达链
外部事件 / AI 识别结果 → 事件中心 → 审核中心 → 流程审核通过 → 转工单 → H5 处置 → 结案

#### 主线 B：任务产出事件链
巡检任务 → 无人机执行 / 采集 → 媒体回传 / 识别 → 生成事件 → 审核中心 → 转工单 → H5 处置

#### 一期与双主线的关系
一期仍按“双主线架构”设计整体产品边界，但建设优先级明确区分为：

- 一期必须跑通：**事件直达链**
- 一期最小预留：巡检任务中心基础建模、任务页面骨架、任务与事件关联关系、无人机平台接入预留
- 二期重点深化：无人机执行回传、任务自动产出事件、任务执行轨迹与更完整的任务闭环

因此，一期产品结构保留“巡检任务中心”，但不要求完成“任务产出事件链”的完整联调闭环。
### 3.3 角色设计

核心角色如下：

- 平台管理员
- 审核员
- 指挥调度员
- 现场处置人员

### 3.4 审核机制

审核按**混合模式流程引擎**设计：

- 单人审核
- 串行审核
- 并行审核
- 不同流程模板支持不同审核模式

当前主场景默认要求：

- 事件进入审核前需选择流程模板
- 流程中的关键节点必须满足通过条件
- 流程整体通过后，事件进入“待派单”状态
- 只有执行派单动作时才正式生成工单

#### 流程模板选择规则

为保证审核一致性，流程模板按以下规则使用：

1. 系统先按事件类型匹配启用中的流程模板
2. 若仅匹配到一个模板，则默认带出该模板
3. 若匹配到多个模板，则由审核员在审核详情页人工选择
4. 流程实例一旦提交，模板版本即被冻结，不允许中途切换模板版本
5. 若事件被驳回后重新提审，默认沿用原模板与原版本；仅管理员或具备授权的审核员可改选新模板

### 3.5 H5 定位

H5 一期聚焦两类能力：

- 工单处置
- 现场核查

不承载完整后台配置和复杂审批能力。

### 3.6 事件与工单关系

采用严格的一对一关系：

- 一个事件只能生成一张工单
- 工单必须来源于已审核通过的事件
- 首期不支持拆单
- 首期不支持并单

### 3.7 系统边界

本期系统按“主体闭环 + 少量关键外部对接”建设。

重点外部对接对象：

- 无人机平台
- 地图服务

其他外部系统统一采用接口预留与配置化扩展方式。

### 3.8 Web 信息架构

Web 端采用混合式组织方式：

- 一级菜单按业务域稳定划分
- 首页 / 驾驶舱按角色展示待办、快捷入口、统计
- 通过权限控制菜单、按钮和数据范围

### 3.9 流程中心定位

流程中心按**独立流程中心**设计，但产品菜单层面可以与审核中心紧密相邻，便于业务使用。

## 6. 核心业务流程

## 6.1 事件直达转工单流程

外部事件接入 → 事件入库 → 进入审核中心 → 选择流程模板 → 节点审核 → 流程通过 → 事件进入待派单 → 执行派单 → 生成工单 → H5 处理 → Web 办结确认

关键规则：

- 事件入库初始状态为待审核
- 审核通过后，事件先进入“待派单”状态，但此时尚未生成工单
- 只有调度员执行派单动作时，系统才正式生成唯一工单
- 工单生成后初始状态为“待接单”
- 事件进入“已转工单”状态后，不可再次生成新工单
- 工单处理完成后事件进入闭环完成态

#### 事件接入规范（一期最小要求）

一期至少支持“无人机平台 / AI 识别结果”两类事件进入系统，最小接入契约应包括：

- 外部事件唯一标识，用于幂等去重
- 事件来源类型
- 事件类型
- 事件标题 / 描述
- 发生时间
- 位置坐标 / 行政区域
- 至少一个证据引用（图片、视频或识别截图）
- 来源系统标识

接入方式以接口推送为主，后端需具备幂等校验、重复事件过滤、失败记录与重试预留能力。
## 6.2 巡检任务产出事件流程

创建巡检任务 → 绑定设备 / 区域 / 时间 → 无人机执行 → 回传图片 / 视频 / 识别结果 → 生成事件 → 进入审核中心 → 转工单 → H5 处置

关键规则：

- 一个任务可产出多个事件
- 任务完成不等于工单闭环完成
- 事件需保留来源任务标识

## 6.3 混合审核流程

- 事件进入审核中心后选择流程模板
- 生成流程实例和节点实例
- 节点支持单人 / 串行 / 并行规则
- 关键节点全部满足通过条件后，流程整体通过
- 任一关键节点驳回，流程进入驳回态

## 6.4 H5 处置闭环流程

工单派发 → H5 待办接收 → 接单 → 到场核查 / 现场处置 → 上传图片 / 视频 → 填写说明 → 提交结果 → Web 确认办结

#### 派单与接单机制

一期采用“**派给具体人员，接单确认生效**”的模式：

- Web 调度员将工单直接派发给具体现场处置人员
- 工单派发后进入“待接单”状态，并出现在该人员 H5 待办中
- H5 端由被派发人员执行“接单”动作后，工单进入“处理中”
- 一期不支持抢单模式
- 改派允许发生在“待接单”与“处理中”状态，由调度员在 Web 执行
- 若超时未接单，可触发催办或改派

#### 核查结论与状态迁移

H5 核查或处置提交后，按以下规则影响工单与事件：

| 核查/处置结果 | 工单状态变化 | 事件状态变化 | 后续动作 |
| --- | --- | --- | --- |
| 属实并已处理 | 待办结确认 | 保持已转工单 | Web 进行办结确认 |
| 属实但需继续处理 | 处理中 | 保持已转工单 | 继续现场处置 |
| 不属实 | 已关闭 | 已关闭 | 记录核查结论并结束闭环 |
| 需补充 | 待核查 | 保持已转工单 | 补充证据后再次提交 |
| 办结确认不通过 | 处理中 | 保持已转工单 | 退回现场继续处理 |

其中“属实并已处理”与“提交办结申请”绑定，只有提交办结申请后，工单才进入“待办结确认”。

## 7. 核心领域模型与状态机

## 7.1 核心对象

建议围绕以下对象建模：

- User 用户
- Role 角色
- Event 事件
- PatrolTask 巡检任务
- ProcessTemplate 流程模板
- ProcessInstance 流程实例
- WorkOrder 工单
- MediaEvidence 媒体证据
- DroneDevice 无人机设备

## 7.2 关键关系

- 一个用户可关联多个角色
- 一个巡检任务可产出多个事件
- 一个事件可关联多个媒体证据
- 一个事件最多绑定一个流程实例
- 一个流程模板可生成多个流程实例
- 一个事件只能生成一张工单
- 一个工单可包含多条流转记录、处置记录、核查记录

## 7.3 状态机建议

### 事件状态
- 待审核
- 审核中
- 审核通过
- 审核驳回
- 待派单
- 已转工单
- 已关闭

推荐流转：

待审核 → 审核中 → 审核通过 → 待派单 → 已转工单 → 已关闭

驳回后允许：

审核驳回 → 待审核

### 巡检任务状态
- 待执行
- 执行中
- 已完成
- 已取消
- 执行异常

### 流程实例状态
- 待提交
- 审核中
- 已通过
- 已驳回
- 已终止

### 节点实例状态
- 待处理
- 处理中
- 已通过
- 已驳回
- 已跳过
- 已超时

### 工单状态
- 待接单
- 处理中
- 待核查
- 待办结确认
- 已办结
- 已关闭
- 已超时

说明：
- “待派单”只属于事件状态，不属于工单状态
- 工单只在执行派单动作时创建，创建后初始状态固定为“待接单”

### SLA 与超时规则

一期为流程节点与工单均配置基础 SLA 规则，但不做复杂升级编排。

#### 流程节点 SLA
- 配置维度：按流程模板中的节点配置
- 计时起点：节点进入“待处理”时
- 计时终点：节点处理完成时
- 超时结果：节点标记为“已超时”，并在审核中心提示催办

#### 工单 SLA
- 配置维度：按工单类型或事件类型配置
- 待接单计时起点：派单完成时
- 处理中计时起点：接单完成时
- 计时终点：进入“待办结确认”或“已关闭”时
- 超时结果：工单标记为“已超时”，支持调度员催办或改派

一期阶段，超时以“标记 + 催办 + 人工改派”为主，不引入复杂自动升级流转。

## 11. 一期建设范围建议

## 11.1 一期目标

先跑通完整业务闭环：

**事件进入 → 审核流程 → 转工单 → H5 现场处置 / 核查 → Web 办结确认**

## 11.2 一期必须建设

### 后端
- 登录认证
- 用户角色权限
- 事件中心
- 审核中心
- 流程中心
- 工单中心
- 文件上传
- H5 待办与处置接口
- 无人机平台基础接入（事件接入为主）
- 地图基础展示接口
- 日志审计
- 巡检任务基础模型与任务-事件关联预留

### Web
- 登录页
- 首页驾驶舱
- 事件列表 / 详情
- 审核列表 / 详情
- 流程模板列表 / 编辑
- 工单列表 / 详情
- 无人机档案列表
- 地图指挥页
- 用户角色权限页
- 巡检任务列表 / 详情骨架页（用于保留双主线产品结构）

### H5
- 登录页
- 工作台
- 工单列表
- 工单详情 / 处置页
- 现场核查页
- 历史记录页
- 我的页

### 一期范围说明
- 一期验收以“事件直达链完整闭环”为准
- 巡检任务中心在一期保留基础建模、页面骨架和任务-事件关系，但不要求完成“任务自动产出事件”的完整外部联调闭环
- 因此，一期是“闭环优先 + 双主线预留”，二期再深化任务产出事件链
## 11.3 建议二期建设

- 复杂地图分析能力
- 复杂无人机控制能力
- 多渠道消息通知
- 高级统计报表
- 条件分支 / 子流程 / 可视化流程设计器
- 更多外部系统深度集成

## 11.4 推荐开发顺序

1. 后端核心域先行（权限、事件、流程、审核、工单、文件）
2. Web 核心业务页（审核、流程、工单、事件）
3. H5 闭环页（接单、核查、上传、反馈）
4. 补首页驾驶舱、地图、设备管理
5. 补系统治理、日志、接口配置增强

---

## 12. 推荐方案结论

最终推荐方案为：

### 产品架构
采用**平台化双主线架构**：

- 事件中心
- 巡检任务中心
- 审核中心
- 流程中心
- 工单中心
- 无人机接入中心
- 地图指挥中心
- 系统管理
- H5 现场闭环端

### 技术架构
采用**三项目 + 模块化单体后端**模式：

- Spring Boot 后端
- Vue3 Web 管理端
- Vue3 + Vant H5 端

### 一期建设策略
以“闭环优先”作为核心原则，优先完成：

**事件 → 审核 → 流程 → 工单 → H5 处置/核查 → 办结确认**

这是当前最符合业务诉求、最容易落地、也最适合后续持续扩展的方案。
