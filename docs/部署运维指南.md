## 二、快速部署（本地开发）

### 1. 获取项目代码

项目位于服务器 `/uav_data`（git 远程：`https://github.com/lxxyyy29/lsc.git`）。

```bash
cd /uav_data
```

### 2. 配置环境变量

创建 `.env` 文件：

```env
# 数据库
DB_URL=jdbc:mysql://127.0.0.1:3306/zhsq?useUnicode=true&characterEncoding=utf-8&serverTimezone=Asia/Shanghai
DB_USERNAME=root
DB_PASSWORD=your_password

# MongoDB
MONGODB_HOST=127.0.0.1
MONGODB_PORT=27017
MONGODB_DATABASE=alarm_dgcp

# Redis
REDIS_HOST=127.0.0.1
REDIS_PORT=6379
REDIS_PASSWORD=your_password
REDIS_DATABASE=7

# JWT
JWT_SECRET=your-secret-key-here

# MinIO
OSS_ENDPOINT=http://127.0.0.1:9009/
OSS_ACCESS_KEY=admin
OSS_SECRET_KEY=your_minio_secret
OSS_BUCKET=dgcp-oa

# 安全
APP_TEST_ENABLED=false
```

### 3. 启动依赖服务

以下为 Windows 示例；Linux 服务器实际采用 Docker 容器（dgjr-mysql/redis/mongodb/minio），见下文生产部署。

```bash
# MySQL（Windows）
net start MySQL

# MongoDB
net start MongoDB

# Redis
redis-server

# MinIO
minio server C:\minio-data --console-address ":9001"
```

### 4. 启动后端

```bash
cd backend
./mvnw spring-boot:run
```

### 5. 启动前端

```bash
# Web 管理端
cd web
npx pnpm install
npx pnpm dev --host 0.0.0.0 --port 5175

# H5 移动端
cd h5
npx pnpm install
npx pnpm dev --host 0.0.0.0 --port 5174

# 小程序
cd mp
npx pnpm install
npx pnpm dev --host 0.0.0.0 --port 5176
```

## 三、生产部署

生产环境实际采用 `docker/` 目录的 docker-compose 一键部署（详见 `docs/部署实操指南.md`），容器与端口：

| 容器 | 对外端口 |
|------|---------|
| dgjr-backend | 9072 |
| dgjr-web | 9071 |
| dgjr-h5 | 9073 |
| dgjr-mp | 9074 |

数据持久化在宿主机 `/uav_data/data/` 与 `/uav_data/uploads/`。

以下为不用 Docker 时的手动打包方式（仅供参考）：

### 后端打包

```bash
cd backend
./mvnw clean package -DskipTests
java -jar target/platform-0.0.1-SNAPSHOT.jar
```

### 前端打包

```bash
# Web 管理端
cd web
npx pnpm build
# 产物在 dist/ 目录，部署到 Nginx

# H5 移动端
cd h5
npx pnpm build

# 小程序
cd mp
npx pnpm build
```

### Nginx 配置示例

```nginx
server {
    listen 80;
    server_name your-domain.com;

    # Web 管理端
    location / {
        root /var/www/web/dist;
        index index.html;
        try_files $uri $uri/ /index.html;
    }

    # API 代理
    location /api/ {
        proxy_pass http://localhost:8080/api/;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }

    # 媒体文件
    location /media/ {
        proxy_pass http://localhost:8080/media/;
    }
}
```

## 五、常见问题

### 1. 端口占用

```bash
# Linux：查找占用端口的进程
ss -tlnp | grep :8080

# Windows：
netstat -ano | findstr :8080
taskkill //F //PID <PID>
```

### 2. MongoDB 连接失败

检查 MongoDB 是否启动：
```bash
mongosh --eval "db.version()"
```

### 3. 文件上传失败

检查 MinIO 是否运行，bucket 是否存在：
```bash
mc alias set local http://127.0.0.1:9009 admin password
mc mb local/dgcp-oa
```

### 4. 测试接口暴露

确保生产环境 `APP_TEST_ENABLED` 未设置或设为 `false`。

## 八、安全建议

1. **修改默认密码**：首次登录后立即修改 admin 密码
2. **JWT 密钥**：生产环境使用随机生成的强密钥
3. **HTTPS**：生产环境必须启用 HTTPS
4. **防火墙**：仅开放必要端口
5. **定期备份**：设置定时备份任务
6. **日志审计**：定期检查操作日志

## 九、多服务器更新流程（两种部署方式）

同一份代码可能部署在多台服务器上，且**部署方式不同**。更新时务必按各自方式操作，否则会出现
"代码已经推送，但某台服务器仍跑着旧版本"的情况。

### 9.1 两种部署方式的区别

| 对比项 | A 类：jar 包部署 | B 类：git 拉取部署 |
|---|---|---|
| 代码来源 | 手动上传的 `backend/target/*.jar` | `git pull` + 服务器上构建 |
| 需要构建工具链 | 不需要（无 JDK/Maven/Node 也能跑） | 需要 JDK 17 + Maven（改前端还需 Node 18+） |
| 推送代码后如何生效 | **换 jar**（`git pull` 对它无效） | `git pull` + 重新打包 |
| 前端产物 | 上传 `web/dist`、`h5/dist/build/h5`、`mp/dist` | 服务器上 `npm/pnpm run build` |
| 环境差异 | 各自 `docker/.env` | 各自 `docker/.env` |

> **关键认知：代码在 git 里，环境在 `.env` 里。**
> `.env`、`backend/target/`、`web/dist/`、`h5/dist/`、`mp/dist/` 均在 `.gitignore` 中，
> 因此 `git pull` 既不会覆盖任何服务器配置，也不会带来构建产物
> （`docker/Dockerfile.backend` 只 `COPY target/*.jar`，`Dockerfile.frontend` 只 `COPY` 各端 `dist`）。

### 9.2 判断某台服务器属于哪类

```bash
cd /uav_data/dgjr
git remote -v && git log --oneline -1    # 有输出 = B 类（git 拉取）；无仓库/报错 = A 类（jar 上传）
which java mvn node 2>/dev/null          # 有 mvn = 具备服务器自建能力（B 类特征）
ls -lh backend/target/*.jar              # jar 时间戳 = 最后一次上传/构建时间
grep -E '^(DOMAIN|WEB_PORT|BACKEND_PORT|DRONE_API_SERVER|DRONE_API_FIXED_WORKSPACE_ID)=' docker/.env
                                         # ↑ 这行才是"环境身份"：该机指向哪个域名/平台
```

### 9.3 一次代码更新，两种方式分别怎么做

**A 类（jar 部署）**

```bash
# ① 本地构建并上传（服务器没有 JDK/Maven 时走这条）
cd backend && ./mvnw clean package -DskipTests        # Windows: mvnw.cmd
scp backend/target/platform-0.0.1-SNAPSHOT.jar root@<A服务器>:/uav_data/dgjr/backend/target/

# ② 服务器上重建后端镜像
cd /uav_data/dgjr/docker
ls -lh ../backend/target/*.jar                        # 确认是新 jar（约 103MB，含 BOOT-INF/）
docker compose build dgjr-backend && docker compose up -d dgjr-backend
```

**B 类（git 拉取）**

```bash
cd /uav_data/dgjr
git status                                            # 先确认无本地改动，避免 pull 冲突
git pull
cd backend && ./mvnw clean package -DskipTests        # 打包前停掉后端更稳：jar 被占用时 clean 会失败
cd ../docker && docker compose build dgjr-backend && docker compose up -d dgjr-backend
docker compose logs --tail 60 dgjr-backend            # 确认 Flyway 迁移与启动日志正常
```

**前端**：仅当改动涉及 `web/`、`h5/`、`mp/` 时才需要重建；只改后端 Java 时两台都跳过。

### 9.4 `.env` 变更也要各自处理

`.env` 不随 git 走，**新增配置项必须在每台服务器上手动追加**，并且改完要
`docker compose up -d dgjr-backend`（`docker compose restart` 不会重新读取 `.env`）。

### 9.5 推送约定：提交信息必须带「部署提示」

本仓库约定：推送时在提交信息末尾附一段 **【部署提示】**，写清两种部署方式各自要做什么，例如：

```
feat(xxx): 某某功能

【部署提示】
- A 服务器（jar 包部署）：上传 backend/target/*.jar → docker compose build dgjr-backend && up -d
- B 服务器（git 拉取部署）：git pull → cd backend && mvnw clean package -DskipTests → docker compose build dgjr-backend && up -d
- 前端：本次无需重建（只改后端 Java）
- .env：新增可选项 XXX（默认关闭，不配则不生效）
```

**目的**：看提交记录即可知道"哪台服务器该做什么"，避免两种部署方式混淆。
