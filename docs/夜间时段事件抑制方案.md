# 夜间（可配置时段）事件抑制方案

> 目标：在**后台可自助调整时段**的前提下，让落在指定时段内上传的事件**不进入正常展示/派单/通知流程**，数据不丢失、可追溯、可回滚。
>
> 版本：v2（2026-10-17）｜状态：**已上线**（202.168.190.132）
>
> ⚠️ **政策变更（2026-10-17）**：v1 的「时段结束自动恢复可见」**已废弃**。
> 上线后实测：10-16 夜间（17:30–09:00）共抑制 118 条无人机违停抓拍，09:00 到点全部自动恢复，
> 白天一次性涌入事件列表/大屏，等于没有静默（业务反馈原话「昨天晚间的事件还能看到」）。
> **现行行为（B 方案）**：
> 1. 夜间抑制的事件**白天也保持 `hidden=1`**，不进入列表/大屏/GIS/统计，也不参与派单；
> 2. 窗口结束**不再自动恢复**，只在业务需要时由人**放出**：事件闭环处置页勾选「只看夜间抑制」
>    → 单条「放出」或顶部一键「放出待放行 N 条」（`PUT /api/events/suppress-manual/release-pending`，单次上限 500）；
> 3. `suppress_released_at` 语义改为**人工放出时间**（窗口结束不写），`suppress_manual=1` 表示已放出；
> 4. 放出后按正常事件处理（此时窗口已结束，`NO_DISPATCH`/`NO_NOTIFY` 自然不再拦截）。
>
> 下文凡涉及「到点自动恢复 / 时段结束自动可见」的表述（§二.4、§3.3.3、§四 用例 4、§六）**均以本节为准**。

## 一、现状与结论

| 检查项 | 结果 |
|---|---|
| 后端代码 | 全仓无 `夜间/night/免打扰/quiet hour` 相关实现，也无按小时判断的业务逻辑 |
| 服务器配置 | `.env`、后端容器环境变量均无时段/夜间配置 |
| 数据库 | `sys_config` 仅 2 项（地图中心点）；`biz_dispatch_rule` 13 条仅"事件类型→派单角色"，**无时段字段** |
| 运行痕迹 | `biz_event.hidden=1` 记录 **0 条**（共 55 条）→ 从未有事件被隐藏 |

**结论**：该功能**当前不存在**，需新建。现有 `hidden/archived/deleted` 是**人工**语义字段，本方案**不混用**，另立标记。

## 二、行为定义（需求口径）

1. **时段可配置、可多个、可跨天**
   - 支持多条时段（如 `22:00–07:00` 夜间、`12:00–14:00` 午休），每条可单独启用/停用。
   - 跨天时段（开始 > 结束）自动按"跨零点"处理，例如 `22:00–07:00` = 当天 22:00 至次日 07:00。
   - 每条时段可指定**生效星期**（默认周一至周日）。
2. **三种抑制动作，可组合**
   - `HIDE`：不在事件列表/大屏/地图/统计中显示（**数据照常入库**）。
   - `NO_DISPATCH`：不自动派单（不生成工单）。
   - `NO_NOTIFY`：不推送站内通知/短信。
3. **例外（白名单）**：满足任一条件的事件**不受抑制**
   - 紧急程度为 `RED`（可配置哪些等级豁免）
   - 指定事件类型（可配置）
   - 指定来源系统（如 `12345` 热线转办默认豁免）
   - 人工在后台"强制放出"（单条覆盖）
4. ~~**时段结束自动恢复**：无需人工操作，窗口一过即恢复可见（见 §3.3 的实现方式）。~~
   → **已变更（2026-10-17）**：窗口结束不恢复，保持隐藏直到人工放出，见文首「政策变更」。
5. **可追溯**：被抑制的事件在列表中带"夜间抑制"标记，管理端可按标记筛选查看；审计日志记录**配置变更**（谁在什么时候把时段从 A 改成 B）。

## 三、技术设计

### 3.1 数据模型

**新表 `sys_suppress_window`（时段抑制规则，可后台增删改）**

```sql
CREATE TABLE sys_suppress_window (
  id            BIGINT       NOT NULL AUTO_INCREMENT,
  name          VARCHAR(64)  NOT NULL COMMENT '规则名称，如：夜间静默',
  start_time    TIME         NOT NULL COMMENT '开始时间',
  end_time      TIME         NOT NULL COMMENT '结束时间（小于开始时间表示跨天）',
  weekdays      VARCHAR(20)  NOT NULL DEFAULT '1,2,3,4,5,6,7' COMMENT '生效星期',
  action        VARCHAR(64)  NOT NULL DEFAULT 'HIDE' COMMENT 'HIDE,NO_DISPATCH,NO_NOTIFY 逗号分隔',
  scope_source  VARCHAR(255) NULL COMMENT '限定来源系统，逗号分隔，空=全部',
  scope_type    VARCHAR(255) NULL COMMENT '限定事件类型，逗号分隔，空=全部',
  exempt_urgency VARCHAR(64) NOT NULL DEFAULT 'RED' COMMENT '豁免的紧急等级，逗号分隔',
  enabled       TINYINT      NOT NULL DEFAULT 1,
  remark        VARCHAR(255) NULL,
  created_at    DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at    DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (id)
) COMMENT='时段抑制规则（夜间静默等）';
```

**`biz_event` 增列（记录抑制事实，便于查询过滤与追溯）**

```sql
ALTER TABLE biz_event
  ADD COLUMN suppress_until DATETIME NULL COMMENT '抑制截止时间：该时间前不展示/不派单；NULL=未抑制',
  ADD COLUMN suppress_rule_id BIGINT NULL COMMENT '命中的抑制规则ID',
  ADD COLUMN suppress_manual TINYINT NOT NULL DEFAULT 0 COMMENT '人工强制放出：1=不受抑制';
```

**`sys_config` 增项（全局开关，便于应急一键关闭）**

| config_key | 默认 | 说明 |
|---|---|---|
| `suppress.enabled` | `1` | 总开关，关掉后所有时段规则失效（应急用） |
| `suppress.timezone` | `Asia/Shanghai` | 判定时区 |

### 3.2 后端改动

**新增文件**

| 文件 | 职责 |
|---|---|
| `modules/system/entity/SuppressWindowEntity.java` | 规则实体 |
| `modules/system/mapper/SuppressWindowMapper.java` | CRUD（JdbcTemplate，与现有风格一致） |
| `modules/system/service/SuppressWindowService.java` | 规则 CRUD + `evaluate(sourceSystem, eventType, urgency, occurredAt)` 命中判定（跨天/星期/白名单） |
| `modules/system/controller/SuppressWindowController.java` | `/api/system/suppress-windows` 增删改查 + 启停 + 测试接口 |
| `db/migration/V133__suppress_window.sql` | 建表 + `biz_event` 增列 + `sys_config` 项 + 权限行/菜单授权 |

**生效点（三处，均调用 `SuppressWindowService.evaluate`）**

1. **入库即抑制**：`modules/integration/alarm/service/ThirdPartyAlarmIngestService.ingest(...)`
   - 命中 `HIDE` → 写入 `suppress_until`（= 命中时段的结束时刻）、`suppress_rule_id`
   - 命中 `NO_DISPATCH` → 跳过自动派单分支
   - 命中 `NO_NOTIFY` → 跳过通知推送
2. **统一查询过滤**（保证"不显示"在各处一致）
   - SQL 侧：`EventMapper`/大屏统计等查询统一追加
     `AND (e.suppress_manual = 1 OR e.suppress_until IS NULL OR e.suppress_until <= NOW())`
   - **Mongo 侧**（事件列表/大屏数据源为 MongoDB，需同步）：
     `alarm_events` 文档写入 `suppressUntil` 字段，查询追加
     `$or: [{suppressManual:true},{suppressUntil:{$exists:false}},{suppressUntil:{$lte:new Date()}}]`
   - 需覆盖的接口清单：`/events`、`/events/sections/*`、`/community/dashboard/big-screen(-events)`、`/community/dashboard/grid-stats`、地图热力/聚合接口
3. **自动恢复**：~~无需定时任务 —— `suppress_until` 到点后查询条件自然放行（推荐）~~
   → **已废弃（2026-10-17）**。实际实现改为「复用 `hidden` 字段」：入库时写 `hidden=1`，窗口结束**不改**，
   只有人工放出才置 `hidden=0`（`suppress_manual=1` + `suppress_released_at=NOW()`）。
   `SuppressReleaseTask` 不再写库，仅每分钟统计「待放行」条数并在变化时打日志。

## 四、验收用例（部署后逐条实测）

| # | 用例 | 期望 |
|---|---|---|
| 1 | 配置 `22:00–07:00` + `HIDE`，造一条 **23:30** 的模拟告警回调 | `biz_event`/Mongo 有记录，但列表/大屏/地图**查不到**；`suppress_until`=次日 07:00 |
| 2 | 同上，改为 **10:00** 的回调 | 正常可见、正常派单 |
| 3 | 紧急等级 `RED` 在豁免列表时，夜间回调 | **正常显示**（白名单生效） |
| 4 | 时间推进到次日 07:00 之后 | **（2026-10-17 起）保持隐藏**，仅在「只看夜间抑制」里可见，需人工放出 |
| 5 | 在后台把时段由 `22:00–07:00` 改为 `23:00–06:00` | 立即生效（无需重启）；审计日志有配置变更记录 |
| 6 | 关闭该规则开关 | 后续夜间回调全部正常显示 |
| 7 | 事件详情点"强制放出" | 该条立即可见，其他同批仍被抑制 |
| 8 | 时段设 `NO_DISPATCH` | 夜间事件可见但**不生成工单**；白天恢复派单 |
| 9 | 跨天时段 `23:00–05:00` 在 **01:00** 触发 | 命中（跨天算法正确） |
| 10 | 非生效星期（如仅周一）在周二触发 | 不命中 |

## 六、风险与回滚

- **回滚**：① `sys_config.suppress.enabled=0` 立即全局失效（应急）；② 删除规则行；③ 迁移级回滚：`DROP TABLE sys_suppress_window` + `ALTER TABLE biz_event DROP COLUMN suppress_*`（迁移前自动备份 jar 与库，见下）
- **数据零丢失**：仅打标记，不删不改原始内容；`suppress_until` 到点自动放行
- **一致性地雷**：事件列表/大屏来自 **MongoDB**，SQL 过滤要同步 Mongo，否则会出现"列表看不到、大屏看得到"（§3.2 已列为必改项）
- **时区**：判定统一用 `Asia/Shanghai`，避免容器 TZ 差异（`docker/.env` 已设 TZ）
- **部署前备份**：`mysqldump` 全库 + `/uav_data/backup/` 存 jar、`web/dist`、`docker-compose.yml`、`.env`
